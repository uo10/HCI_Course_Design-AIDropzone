# 命名重生成功能计划

> 读者：前端开发 · 约束：**只改 `frontend/`** · 接口字段见 [后端接口一览.md](./后端接口一览.md)

让用户能**长期定命名风格**、对单个文件**临时补充要求**、不满意时**重算建议名**；重算**不改磁盘**，只有「确认改名」才动文件。

---

## 1. 要完成什么（需求）

| 编号 | 用户要什么 | 成功时 |
|------|------------|--------|
| **R1** | 命名风格（常驻） | 设置里有一段长期说明；之后每次 AI 命名都会参考它 |
| **R2** | 单次补充（临时） | 某个文件不满意时，可写「这次特别强调什么」再算一版 |
| **R3** | 重新生成 | 详情页一键重算建议名/摘要；**文件仍在原处**，直到用户确认改名 |

**原则**

- 重新生成 = 只改**建议**；确认改名 = 才改**磁盘**。
- 风格存在后端 `config`（`naming_style_prompt`）；单次说明**不**写入配置。

**提示词叠加（产品向）**

> 发给模型 ≈ 后端内置默认 + 设置里的风格说明 +（重生成时）本次补充说明

后两项均可为空。

## 3. 怎么完成（实现思路）

### 3.1 旅程 A：设置页保存风格（R1）

1. 打开设置 → `GET /config` 读 `naming_style_prompt`
2. 用户编辑多行说明 → 保存时 `PUT /config` 带上该字段
3. 之后 `POST /parse` / `POST /parse/regenerate` 由后端自动读取 config，前端不用再传风格

**前端文件**：`SettingsView.tsx`、`api/client.ts`（config 类型）

### 3.2 旅程 B：拖入首次命名（已有）

- `POST /parse`，逻辑在 `useFileStore.runParse`
- 解析成功时把 `FileMetadata` 存到 `FileItem.parseMetadata`，供重生成使用

### 3.3 旅程 C：详情页重新生成（R2 + R3）

1. 用户点「重新生成」→ 弹窗填 `extra_prompt`（最长 500 字，可空）
2. `POST /parse/regenerate`：`file`（来自 `parseMetadata`）+ `extra_prompt` + `context_tags`（当前详情页标签）
3. 成功：更新 `suggestedName`、`categoryReason`；**标签保留用户已编辑的**（不强制覆盖 API 返回的 tags）
4. **不调用** `/rename`

**前端文件**：`FileDetailPanel.tsx`、`useFileStore.regenerateFile`、`dropzoneApi.regenerateOne`

**Mock 模式**：不请求后端；按钮禁用并提示使用 `electron:dev:full`。

## 5. 验收

1. `electron:dev:full` + uvicorn → 设置保存风格 → 拖入新文件 → 建议/摘要体现风格（Mock 引擎时 summary 会出现「风格要求」字样）。
2. 详情页填单次说明并重生成 → 建议名变化，磁盘路径不变。
3. 仅「确认改名」后文件才被移动/重命名。
4. 清空设置页风格并保存 → 重生成只受本次 `extra_prompt` 影响（若填写）。
